## 0. 背景与定位演化（最重要的事先讲）

页面当前对应 v0.1.1，时间点是「打通流程 + Windows 修复」。
v0.1.2 不是又加几个功能，是把**生成质量**从「能用但谁也不会真用」改造为「用户配置的模板能真正生效」。

**项目叙事的演化（建议你在页面整体语气上反映这条线）：**

| 版本 | 阶段 | 关键词 |
|---|---|---|
| v0.1.0 | 把链路打通 | 自动化 |
| v0.1.1 | Windows 用户开箱即坏修复 | 稳定 |
| **v0.1.2** | **生成质量大改** | **精准 · 用户掌控** |

页面现状偏向"工具型应用最容易陷入过度工程，我做了减法"的叙述（这是好的，保留）。
v0.1.2 可以**在不破坏这个 tone 的前提下，多加一层「不只是少，还要准」**——
不是更多功能，而是把已有功能调到能让用户真愿意用。

页面现有 tone（"克制、技术博客、重思考过程多于功能罗列"）非常好，**请尽可能保留**。
不要把 v0.1.2 的改动写成营销卖点；按现有那种「我反复掂量过的决定」的口吻继续讲。

- 发布日期（如有显示）：`2026-05-27`

### 1.2 modules 区标题数字 + 副标题

- 现状：`11 个模块,v0.1.1 已全部上车`
- 改成（保守版）：`11 个模块,v0.1.2 全部上车 + 4 处生成质量改进`
- 或（如果你愿意扩到 12 个模块卡片，见 §2）：`12 个模块,v0.1.2 全部上车`

### 1.3「风格记忆」这条模块卡是错的，必须改

- **现状描述**：「把过往周报当作参考样本（默认最近两期），让每一期在用词、结构、详略上保持连贯。」
- **真实情况**：v0.1.2 起，**历史报告默认不再注入** prompt。原因是历史报告会反向"污染" LLM 的格式判断——
  即使用户切换到了另一个模板，LLM 仍会照搬历史报告的章节结构，让用户的 `extra_prompt` 形同虚设。
- **修复方案二选一**：

  **方案 A（推荐，最少改动）**：把卡片标题与描述都改成"可选的风格记忆"，把默认行为说清楚。
  ```
  标题：风格记忆（可选）
  描述：可选地把过往周报作为风格参考注入。默认关闭——历史报告会反向"压制"
        用户当前模板的格式约束，让自定义模板形同虚设。需要时通过 settings 打开，
        启用后仅取同模板生成的历史报告，最大程度减少污染。
  ```

  **方案 B**：直接把这张卡片换成"格式忠实"（见 §2.1 新模块建议）。

  > 倾向方案 A：保留"风格记忆"作为一个能力点，但把默认值改对、把语义说清楚。

### 1.4「项目背景注入」描述过时

- **现状**：「生成前先扫工作区根目录的 md 文档（README / AGENTS.md / CLAUDE.md...），作为项目背景塞进 prompt」
- **真实情况（v0.1.2）**：
  - 扫描范围从「项目根目录 `*.md`」扩到「项目根 + `doc/docs/` 子目录，最大深度 2 层」
  - 子目录名大小写不敏感（`doc / Doc / DOC / docs / Docs / DOCS`）
  - 每个 md 文件按 mtime 分**强信号**（本期内修改 / README* / CLAUDE* / CHANGELOG* / ROADMAP*）
    和**弱信号**（本期未更新的其它 md，仅给文件名 + 首行标题给 LLM 作领域词汇背景，不要据此推断本期成果）
- **改写建议**：
  ```
  标题：项目背景注入（按时间分级）
  描述：生成前扫工作区每个项目的 README / CLAUDE / docs/ 子目录两层 md 文档，
        按修改时间分强弱信号——本期内改过的或核心文档（README 类）给 LLM 看
        完整内容，本期没动的旧文档只给文件名 + 标题作为领域词汇背景。
        LLM 不会把上个季度的设计文档当成本周成果。本机和 SSH 工作区都支持。
  ```

### 1.5 try it 区 CTA 文案

- 现状：`v0.1.1 三平台安装包齐备(含 macOS Swift 原生版社区分支)。 配 LLM 源、加工作区、跑一次, 下一个周末的报表就能自己写好飞进邮箱。`
- 改成：把版本号 `v0.1.1` → `v0.1.2`，其余可不动。

### 1.6 footer / meta 区（如有）

- 如果有 build date / last updated 字段，更新为 `2026-05-27`。

## 2. 建议改：模块列表对齐 v0.1.2

页面目前 11 张模块卡片。v0.1.2 加了几个有"叙述价值"的能力，可以**新加 1-2 张卡，
拆改 1 张**。下面按重要度排：

### 2.1 新模块（强烈建议加）：「格式忠实」

这是 v0.1.2 最核心的修复，必须在页面占位置。

```
标题：格式忠实
图标建议：lucide-stamp / lucide-shield-check
描述：你的模板配的 extra_prompt（含具体格式示例），就是输出格式的最终权威。
      v0.1.2 把它从 prompt 末尾的"额外要求"小节上提到顶部，包成
      <format_spec must_follow="true">，明示 LLM 严格照搬其句式、长度、
      编号风格。同时删除了旧版那一组容易反噬的通用规则（"做了一些工作"
      之类的禁词清单——anti-prompt 反而引导模型把禁词写进去）。
      内置 tech/exec/simple 三个 style 也尊重 extra_prompt：你给了示例，
      就不再叠加内置风格细则。
```

### 2.2 新模块（建议加）：「两轮 LLM 模式（可选）」

```
标题：两轮 LLM（可选）
图标建议：lucide-repeat / lucide-shuffle
描述：高质量场景下的可选模式。第一轮让 LLM 从原始 work_logs 提炼出
      "完成事项" JSON 数组（去掉"再试一次""为啥"这类过程性指令），
      第二轮基于提炼的事项 + 你的模板格式渲染 Markdown。
      代价是 token 翻倍、延迟更长；默认关闭，需要更高质量的人在
      settings.json 里把 generation_mode 改成 "TwoRoundSilent"。
      第一轮 JSON 解析失败时自动 fallback 到单轮，不阻塞。
```

> 注意：UI 还没暴露这个开关，需要手动编辑 settings.json。这点不要写进卡片描述
> （那是实现细节），但如果你的页面有"高级配置"小节可以提一句。

### 2.3 改写现有「指令配对 AI 回复」，补一句"过滤填充词"

- 现状：「不只抓你说了什么,还把每条指令配对抓出 AI 的回复。history.jsonl 与 session 双源去重,过滤掉工具注入噪音(environment_context / turn_aborted 等)。」
- 改成（追加 v0.1.2 的过滤能力）：
  ```
  不只抓你说了什么,还把每条指令配对抓出 AI 的回复。history.jsonl 与 session
  双源去重,过滤掉工具注入噪音（environment_context / turn_aborted），
  以及用户的过程性填充词指令（"好的"/"再试一次"/"嗯"/"OK"）和弱表态回复
  （"好的"/"已收到"）——这些不是真工作内容，留下来反而会污染 prompt。
  ```

### 2.4 「Review 四步可改」的措辞复查（小事）

- 现状描述里有「项目背景 → AI 回复 → 草稿 → 终稿」四步。
- 实际上：项目背景和 AI 回复的"步骤"是同一个 review 界面里的不同选项卡/区块，
  不算独立的四步。也就是说"四步"这个数字可能不严格对应。
- **建议**：保留"Review 可审核"概念，但把"四步"换成更准的描述，比如：
  ```
  Review 可审核 · 草稿自动落盘
  ——
  生成不是黑盒：扫完日志后先进 review 界面，按项目编辑工作指令、
  增删条目、改项目背景文档；生成完成后再进预览，能复制 md 或 html。
  整个流程随时关掉不丢内容（draft 自动落盘）。
  ```
  （也可以保留"四步"如果你确认那是当前 UI 的真实步骤——我没在仓库里查到"四步"这个明确分段，
  你审稿时如有 UI 截图可以核对。）

### 2.5（可选）新增模块：「等待动效」

如果你想凑到 12 张卡（视觉上 4×3 整齐），这是个不重要但 v0.1.2 加的小功能：
```
标题：等待动效
图标建议：lucide-loader / lucide-activity
描述：长操作不再让你瞪着静态文字。生成时显示跳动点 + 不定式进度条 +
      每 1.8 秒切换一条真实的内部阶段 log（"扫描 → 解析 → 去重 → 配对回复
      → 强弱分类 → 调 LLM → 渲染 Markdown"）。让你知道应用没死，
      也顺便展示了内部在做什么。
```

> 这张卡可加可不加。加了凑整数，不加也不影响完整性。

## 3. 建议改：Decisions 区加 2-3 条新决策

页面现有 6 条决策（Tauri / JSON / 多源 LLM / SSH / Review / 项目背景 md）都还成立，**不要动**。
v0.1.2 多了几个值得"反复掂量"的决策，建议在末尾追加。tone 严格按现有 01-06 的风格写：
小标题 + 一句"为什么这是问题" + 一段"我是怎么权衡的"。

### 决策 07（强烈建议）：用户的 extra_prompt 是格式权威，不是建议

```
07
用户的 extra_prompt 是格式权威,不是建议
——
最早的 prompt 设计里,模板的 extra_prompt 被放在 prompt 末尾,
跟"7 条通用规则"、"禁止用语清单"、"历史报告参考"挤在一起。
结果就是:用户认真配了一个自定义模板,LLM 还是照搬技术周报的章节结构。
原因不复杂 —— LLM 看到一堆冲突的格式信号,会挑权威看起来更高的那一份,
而历史报告 + 通用规则的"分量"远比末尾几行说明大。

v0.1.2 起,extra_prompt 上提到 prompt 最顶部,包成
<format_spec must_follow="true">,明示这是格式的唯一权威。
同时删掉了那 7 条通用规则和禁止短语清单 —— 后者尤其反噬,
"不许写做了一些工作"反而会引导 LLM 把这种话写进去。
保留下来的只有 3 条不可妥协的硬约束:禁前言、禁编造数字、禁"(推断)"标签。
```

### 决策 08（建议）：默认不注入历史报告

```
08
历史报告默认不注入
——
最初设计是"风格记忆":把过去两期周报作为参考样本喂给 LLM,
让用词节奏更连贯。听起来无害,实际是个反向污染源:
切换模板时,LLM 仍会照搬旧报告的章节结构,新模板的 extra_prompt 形同虚设。

v0.1.2 把这条默认关掉。需要时仍可在 settings 里开,但开了之后默认
只取同模板生成的历史(避免跨模板污染)。"风格记忆"作为能力点保留,
但默认值改成"不要影响别的版本"。
```

### 决策 09（可选）：两轮 LLM 是可选的，不是默认

```
09
两轮提炼-渲染是可选的,不是默认
——
高质量周报最稳的做法,是先让 LLM 把原始日志提炼成"完成事项" JSON,
再用 JSON 渲染 Markdown。两轮模型看到的输入都已经是事实,
不再有"再试一次""为啥"这种过程指令干扰。

但默认开它就意味着所有用户的 token 用量翻倍、延迟翻倍。
对一个一周才跑一两次的工具,这笔账不能让默认用户付。
所以两轮模式做了 settings 开关,默认 OneRound,
追求质量的用户手动改 generation_mode 启用。
解析失败自动 fallback 单轮,不阻塞。
```

> 决策 09 可加可不加。如果页面想保持 6 条决策的克制感，至少加 07 和 08。

## 5. 不要做的事

- ❌ **不要把 v0.1.2 写成"重大重构"或"全面升级"**。这是个工具型小项目，
  不需要 marketing 腔。按现有 tone（"反复掂量过的决定"）继续写。
- ❌ **不要新增不存在的功能**。两轮 LLM 是可选模式不是默认；
  doc 子目录扫描有深度限制（2 层）；强弱信号是按 mtime 自动判断不是用户配的。
  这些边界要写准。
- ❌ **不要把"风格记忆"卡片完全删掉**。它仍然是个能力点，
  只是默认关闭了。删掉显得能力倒退，改写成「可选」才符合事实。
- ❌ **不要修改 6 条现有决策的文字**。它们仍然成立。
- ❌ **不要承诺没做的事**。比如"未来支持……"、"即将上线……"。
  保持页面只描述当下已发布的事实。

## 6. 仅供参考：v0.1.2 完整改动清单

为防你需要交叉确认。这份清单就是仓库 [CHANGELOG.md](https://github.com/changan593/WeeklyReport/blob/main/docs/CHANGELOG.md#012---2026-05-27) 的浓缩版：

### 改动

| 模块 | 改动 |
|---|---|
| `projectdocs.rs` | 扫描扩到 root + `doc/docs/{*,*/*}.md`（深度 ≤ 2），按 mtime 分强/弱信号 |
| `ssh.rs` | `sync_project_docs` 支持新扫描范围 |
| `logs.rs` | 过滤填充词指令（"好的"/"再试一次"等）+ 过滤弱表态回复（"好的"/"已收到"） |

| `report.rs` | 新增两轮 LLM 模式（extract_achievements → render_from_achievements） |
| `state.rs` | 新增 3 个 Settings 字段：`inject_past_reports` (默认 false)、`past_reports_same_template_only` (默认 true)、`generation_mode` (默认 OneRound) |

| `tailwind.config.js` | 新增 keyframes：`progress-sweep`、`log-fade-in` |
